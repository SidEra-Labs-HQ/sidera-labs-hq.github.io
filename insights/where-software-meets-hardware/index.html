Where software meets hardware: writing interface contracts

Physical systems fail at the seams: between teams, between units, between clocks. Most of those seams can be written down before anything is powered on.

Hardware-software integration · 8 min read · SidEra Labs

Units and frames

A well-known unit failure in engineering is the loss of NASA’s Mars Climate Orbiter in 1999. The Mishap Investigation Board’s Phase I report describes an interface specification that required thruster impulse data in newton-seconds. The ground software supplied it in pound-force seconds, and the verification process did not catch the mismatch. The report also identifies contributing causes beyond the unit error, so the lesson is wider than one conversion: the interface was not verified end to end.

The habit to take from it is cheap. In every interface that carries a physical quantity, state the following in the field name or the type, not only in a document:

  • Unit, for example speed_m_per_s instead of speed.
  • Frame and sign convention, for example “x forward, y left, z up, right-handed”.
  • Valid range, and what happens outside it.
  • Update rate and what “no update” means.

Robotics middleware shows the pattern in practice. In ROS 2, for instance, standard messages carry a header with a timestamp and a coordinate frame identifier, so receivers know when and in what frame a measurement was made. The std_msgs/msg/Header definition contains a stamp field, a time, and a frame_id field, the coordinate frame the data is associated with. The architecture is described by Macenski and colleagues in Science Robotics.

Timing

Software treats time as a detail. Control treats it as part of the signal. Three practices cover most of it.

  1. Timestamp at the source. Stamp a measurement when it was taken, not when it arrived. Arrival time includes queues and jitter you did not intend to measure.
  2. Write a latency budget. Add up each stage from sensor to actuator and compare it with what the control loop can tolerate. As an illustration only: if a loop runs at 100 Hz it has a 10 ms period, so a camera pipeline that adds 60 ms of delay means every decision acts on a world that is already several cycles old.
  3. Measure jitter, not just average latency. A loop that is usually on time and occasionally 50 ms late behaves very differently from one that is always 20 ms late.

Safe states

Define, in advance, what the device does when something goes wrong: a sensor stops reporting, a message is late, software crashes, power dips. For a motor that may mean cutting torque. For a heater it may mean turning off. Then test that path on purpose. Common supports are a hardware watchdog that resets or disables outputs if software stops checking in, hard limits enforced below the software layer, and an emergency stop that does not depend on the code being healthy.

Simulation and reality

Simulation is the fastest way to find logic errors, and it is a poor judge of friction, noise, backlash and thermal behaviour. Use it for what it is good at, then close the gap in stages: replay recorded real data through the software, then run with the real controller and a simulated plant, then the real device with conservative limits, and only then relax the limits. Keep the same interfaces at every stage so that nothing changes but the thing under test.

Log to replay

Physical failures are hard to reproduce. Record raw sensor streams with timestamps, commands sent, internal state and software and configuration versions. With that, a failure can be fed back through the software on a desk. Without it, the only test is waiting for the problem to happen again.

A test ladder

Unit testsPure logic, conversions and state machines. Fast and run constantly.
Replay testsRecorded real data run through the software. Catches regressions on real signals.
Hardware in the loopReal controller, simulated plant. Tests timing and I/O without risk.
Bench testsReal device, conservative limits, a person at the stop button.

The short version. Put units and frames in the names. Timestamp at the source and budget your latency. Decide the safe state and test it. Log enough to replay.
