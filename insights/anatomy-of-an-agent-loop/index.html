The anatomy of an agent loop

An agent is a loop with a model in the middle. Most of what makes it dependable is not the model. It is the code around it.

What counts as an agent

The word “agent” gets used for everything from a chatbot with a calculator to a system that works unattended for hours. A useful distinction, drawn in Anthropic’s engineering guidance on the topic, is between workflows, where models and tools are orchestrated through code paths written in advance, and agents, where the model directs its own process and decides which tools to use and when.

That distinction has a practical consequence. If the steps of a task are known ahead of time, write them as a workflow. It will be cheaper, faster and easier to test. Reach for an agent when the path genuinely cannot be known in advance, and accept the cost in predictability.

The four jobs

One useful way to reason about an agent loop is to separate four jobs.

  1. Observe. Assemble what the model will see: the task, relevant state, recent results.
  2. Decide. Ask the model for the next step, which is either a tool call or a claim that the task is finished.
  3. Act. Run the tool and capture the result, including errors.
  4. Verify. Check the outcome with something that is not the model’s own opinion.

The ReAct paper by Yao and colleagues popularised interleaving reasoning with actions in this way. The sketch below is illustrative pseudocode in a Python-like style. It is not a tested implementation and is not meant to be run as written.

def run(task, tools, budget):
    state = State(task)
    while not budget.exhausted():
        view = state.observe()               # what the model is shown
        step = model.decide(view, tools.specs)
        if step.is_final():
            failures = checks.run(state, step)   # independent of the model
            if not failures:
                return step.result
            state.note(failures)             # feed failures back in
            continue
        result = tools.call(step)            # typed, time-limited, logged
        state.record(step, result)           # durable, outside the model
        budget.charge(step, result)
    return escalate_to_human(state)

Notice what is not in the model’s hands: the budget, the checks, the record and the decision to escalate. Those are ordinary code, and that is deliberate.

State lives outside the model

A model’s context window is a working view, not a database. Anything that must survive, such as what has been done, what was decided and what is pending, belongs in a structure the program owns. The model is shown a selection of it each turn. This makes runs resumable, lets you inspect exactly what the model saw, and stops important facts from silently falling out of context in a long task.

Tools are contracts

A tool is an interface between a probabilistic caller and deterministic code, so it deserves the care of any public API.

  • Typed inputs. Validate arguments before running anything. Reject, do not guess.
  • Error messages written for the caller. “File not found: did you mean report.md?” helps a model recover. A stack trace does not.
  • Idempotence where possible. If a step is retried, it should not do the damage twice.
  • Time limits and size limits. No tool should be able to hang the loop or flood the context.
  • Least privilege. Give each tool access to exactly what it needs. Prefer a read-only tool when reading is enough.

Budgets and stop conditions

A loop without limits is a bug waiting for an input to trigger it. Set explicit ceilings on steps, wall-clock time and cost, and decide in advance what happens when one is hit. Add a check for no progress: if the last several steps repeat an action or produce the same result, stop and escalate rather than burn the whole budget. A clean “I could not finish, here is where I got to” is a valid and valuable outcome.

Verification the loop cannot talk past

A model that says “done” has only told you what it believes. Prefer checks that can fail independently of its reasoning: tests that run, a schema that validates, a diff that stays under an agreed size, a numeric result recomputed by separate code. When no automatic check exists, that is a signal to put a person at the decision point, not to trust the claim.

Untrusted content

Tool results, web pages, documents and emails are data, but a model reads them in the same stream as its instructions. Text inside them can try to redirect it. This is prompt injection, listed as LLM01 in the OWASP Top 10 for LLM Applications, which also distinguishes direct attempts from indirect ones that arrive through content the system fetches.

No single filter solves this. A more dependable approach is structural: limit what the system can do, require confirmation for consequential actions, keep untrusted content away from privileged tools where you can, and assume some injections will get through. These are general recommendations, not guarantees. OWASP’s guidance itself says it is unclear whether foolproof prevention methods exist.

What to log

Record, for every step, what the model was shown, what it chose, the tool call and its result, the budget used, and which checks ran. With that you can replay a failure, see why a decision was made, and measure the loop honestly. Without it, debugging an agent means guessing.

The short version. Keep state, budgets, checks and escalation in ordinary code. Let the model choose steps. Verify with something other than the model.
